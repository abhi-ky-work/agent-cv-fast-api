- Identity documents of business owners and directors

## Major Technical Contributions
### 1. Async Workflow Rewrite — 60% Reduction in Process Time
One of my most impactful contributions was rewriting the account opening 
workflow from a blocking synchronous flow to a fully asynchronous 
architecture. The original process was taking approximately 7 minutes 
end-to-end to complete a current account opening. After the rewrite, 
the same process completed in 3 to 3.5 minutes — a reduction of 
roughly 60%. This directly improved both the user experience for 
relationship managers using the internal tool and the completion rate 
for customers on the DIY platform.
The core issue was that each step in the onboarding flow was waiting 
for the previous step to resolve before proceeding — database writes, 
third-party API calls, document validations — all were chained 
synchronously. I decoupled these into parallel async workflows 
wherever the steps were independent, used queuing for steps that had 
to be ordered, and eliminated unnecessary blocking I/O throughout the 
process.
### 2. DIY Platform — Technical Ownership from Development to Production
After approximately one year at Signzy, I took complete technical 
ownership of a parallel project — the DIY onboarding platform. This 
was a self-serve version of the internal relationship manager tool, 
designed so that business customers could directly initiate and 
complete their current account opening without needing a bank 
relationship manager to facilitate it.
I led this platform from active development through UAT (User 
Acceptance Testing) and all the way to its production launch. This 
involved coordinating with QA teams, managing deployment pipelines, 
aligning with the client bank's compliance and technical teams, and 
resolving blockers across the delivery lifecycle. It was my first 
experience owning a product end-to-end and seeing it go live.
### 3. VKYC and CKYC Integration
One of the most complex integrations I worked on was connecting both 
the internal RM tool and the DIY platform with third-party VKYC (Video 
KYC) and CKYC (Central KYC) providers. 
VKYC is a live video-based process where a bank officer verifies the 
identity and documents of a customer in real time. CKYC is a 
centralised government-backed KYC repository for India where a 
customer's KYC data is stored once and reused across financial 
institutions.
The integration involved transferring the customer from our platform 
to a third-party vendor via SSO, completing the KYC process on the 
vendor's system, and receiving the verified status back into our 
application to proceed with the account opening. Coordinating the 
session handoff, handling failure states, managing token expiry, and 
ensuring compliance with the regulatory requirements of the integration 
were the core engineering challenges here.
### 4. Database Indexing and Root Cause Analysis — 85-90% Failure 
    Rate Reduction
As the platform scaled, we started experiencing recurring database 
failures that were causing account opening processes to fail mid-flow. 
This was happening in production, affecting real users at real banks, 
which meant the pressure to identify and fix the root cause was high.
I led the root cause analysis. The investigation revealed that several 
high-frequency queries were running without the appropriate indexes — 
as data volume grew, these queries were doing full table scans and 
timing out. We had not anticipated the query patterns at the volume we 
were operating at.
The fix involved identifying every under-indexed query across the 
critical onboarding path, designing and implementing targeted database 
indexes, and validating that failure rates dropped. The result was an 
85 to 90% reduction in process failure rates. This experience taught 
me how applications break at scale in ways that are invisible at low 
volume — and how to diagnose and fix them systematically rather than 
reactively.

## Major Technical Contributions
### 1. Authentication and Authorisation Overhaul
When I joined, the platform had a critically broken authentication
module that was causing service endpoints to behave incorrectly under
certain access conditions. I owned the end-to-end investigation and
resolution of this.
The core issue was that inter-service API tokens were using symmetric
encryption, which posed a security risk and was not appropriate for a
platform handling sensitive financial data for regulated institutions.
I transitioned the token encryption from symmetric to RSA-based
asymmetric encryption, implemented graceful error handling throughout
the auth flow, and enabled role-based access control across all GraphQL
service endpoints.
Before moving this to production I validated 90% of functionality
across the affected endpoints. I then personally managed the on-call
for the following deployment — monitoring through Grafana and Argo CD,
watching logs and service health in real time to ensure nothing
regressed. This was my first major production deployment at AccernAI
and the experience that led to me taking full ownership of the staging
release lifecycle going forward.
**Technical challenge:** The tricky part was that the broken auth
module was not failing loudly — it was failing silently in certain
role combinations, causing permissions to behave inconsistently
depending on how the token was issued. Finding all the edge cases
required tracing through the GraphQL resolvers systematically and
testing each role combination explicitly before the release.
### 2. UI Performance Optimisation — Lighthouse Score 70 to 90
The platform's dashboards were data-heavy — displaying processed
outputs from large NLP pipelines, list views of models, taxonomies,
and pipeline results. Several pages had significant performance issues
causing slow load times and poor user experience.
I conducted a systematic performance audit using Lighthouse and
identified two categories of problems:
**Excessive render cycles** — components were re-rendering
unnecessarily on state changes that did not affect them. I refactored
these using component decoupling and targeted React hook optimisation
(useMemo, useCallback, React.memo where appropriate), improving
component visibility speed by 80% as validated by Lighthouse.
**Redis cache handling** — several sections of the UI were making
calls that depended on Redis-cached responses. When the cache was cold
or a key was missing, the application was surfacing raw errors to the
user instead of handling the state gracefully. I decoupled these
components and implemented proper loading states and fallback handling,
so users experienced a clean degraded state rather than broken UI when
cache responses were absent.
The overall Lighthouse performance score across affected pages went
from 70 to 90 as a result of these changes combined.
### 3. QA Release Automation CLI Tool
I noticed a recurring friction point between developers and QA
engineers during release cycles. Every time a deployment was prepared,
QA had to manually chase developers to find out what had moved into the
release, which Jira tickets were included, what endpoints had changed,
and what needed to be tested. This back-and-forth was happening through
Slack threads and was slowing down the pre-production validation
process.
I built an internal CLI tool that automated this entirely. The tool
compared the previous deployed Git tag to the current deployment tag,
extracted all commits in between, mapped them to their associated Jira
tickets, and categorised them as features or bug fixes. The output was
a structured release summary — Jira tickets, descriptions, and affected
areas — that QA could use directly to plan and execute their
pre-production testing.
This eliminated the communication overhead entirely. QA could now open
the tool output, see exactly what moved to the environment, navigate
directly to the relevant Jira tickets, and begin testing immediately.
### 4. Staging Release and Hotfix Ownership
Over the course of my tenure I progressively took on more ownership of

AGENTCV — PROJECT CONTEXT FOR AI AGENT
Project Overview
AgentCV was born out of a practical, real-world challenge I was facing firsthand: managing recruiter inquiries and consistently delivering high-quality, contextual details about my technical background. To solve this, I built an autonomous, conversational AI Proxy Agent designed to act as a virtual interviewer. Recruiters can interact with a live chat window to ask questions about my previous organization choices, work experiences, projects, and technical challenges. The agent dynamically answers in the first person, operating exactly like an AI proxy of myself.
The platform is fully live, open-source, and powered by a high-performance backend architecture designed to eliminate hallucinations by grounding response logic strictly within my unstructured professional data.
Technical Architecture & Implementation
To build a system capable of production-grade conversational accuracy, I engineered a low-latency Retrieval-Augmented Generation (RAG) pipeline from scratch:
* Foundational Learning: Before constructing the agent, I deep-dived into the evolution of machine learning—tracing the lineage from foundational neural networks (ANNs, RNNs) to modern Transformers and Large Language Models—to master how to ground generative AI outputs effectively. 
* Agentic Frameworks & Guardrails: I built the core agent utilizing advanced generative AI frameworks, including CrewAI and LangChain, to orchestrate domain-specific conversational logic and strictly maintain the persona of an AI interview proxy. 
* Vector Infrastructure & Embeddings: I designed an optimized retrieval mechanism using Hugging Face to generate mathematical embeddings from my raw professional data. These high-dimensional vectors are stored and indexed in a specialized vector database (FAISS / ChromaDB) to support semantic chunking and high-accuracy context retrieval. 
* Context Isolation Layer: The RAG pipeline separates data ingestion into two strict streams: my raw CV and a highly detailed, comprehensive context file detailing the exact technical challenges and deep-dive resolutions from my past roles. 
* High-Performance Inference: To ensure immediate, human-like response speeds in the chat interface, I hooked the backend framework up to Groq’s LPU (Language Processing Unit) inference engine. Utilizing hardware-accelerated GPU/LPU inferencing allows the LLM (Llama 3.1) to process data chunks and output answers with ultra-low latency. 
TIKITU — PROJECT CONTEXT FOR AI AGENT
Project Overview
TikiTu is a comprehensive, production-grade DevOps and Full-Stack project engineered to demonstrate advanced system design patterns, cloud infrastructure provisioning, and microservices architecture. The application is a highly scalable, live online event-ticketing platform where organizers can list events and customers can browse, select, and securely purchase tickets.
The primary engineering goal of TikiTu was to build a clean, multi-tenant enterprise-grade system from scratch, explicitly demonstrating how distinct business modules scale, communicate, and deploy in an isolated, cloud-native ecosystem.
Technical Architecture & Functional Modules
The application abandons monolithic structures in favor of a strictly decoupled, event-driven microservices architecture:
* Multi-Platform Flow: The system is split cleanly into dedicated frontends (a Next.js web platform and a React Native cross-platform mobile application) that communicate seamlessly with isolated backend services managed via Nest.js and TypeScript. 
* Decoupled Microservices: The backend is segmented into specialized domain services, including:
   * Partner Microservice: Tailored for event organizers to register franchises, list events, and manage inventory. 
   * User/Customer Microservice: Optimized for high-throughput browsing, search, and checkout bucket creation. 
   * Payment Microservice: An isolated service handling transactional states, secure handoffs, and webhooks. 
   * Routing & Notification Microservices: Managing internal event-driven communication and push notification delivery. 
* Identity & Access Management: I implemented robust platform-wide authentication and authorization utilizing AWS Cognito, separating user-facing access tokens from internal partner-administration roles. 
* Infrastructure as Code (IaC): The entire cloud footprint is fully automated. I used Terraform to provision and configure enterprise AWS infrastructure, orchestrating containers across AWS ECS (Elastic Container Service) and Fargate. 
* Data Layer: Each microservice maintains state using its own optimized PostgreSQL database instance, preserving the database-per-service pattern required for true operational isolation at scale.

Likely Recruiter Questions and Answer Anchors
Q: What inspired you to build AgentCV, and how does it prevent hallucinations? I built AgentCV to solve a personal bottleneck: answering highly repetitive recruiter inquiries about my past technical projects and architecture decisions. To ensure it never invents details, I built a strict RAG pipeline using LangChain and CrewAI. The LLM doesn't guess; it is bounded by a vector database containing semantic chunks of my actual CV and a highly specific context file. If a question falls outside that data, prompt guardrails instruct the agent to gracefully redirect, ensuring 100% factual alignment.
Q: Why did you choose Groq and Hugging Face for the AgentCV project? In an interview context, chat latency kills the user experience. Traditional cloud API inferences can take several seconds to stream a response. By routing the pipeline through Groq's LPU inference engine, I achieved near-instantaneous token generation speeds. I paired this with Hugging Face models to create dense, mathematically accurate embeddings locally before saving them into the vector store, proving that you can build high-performance AI applications cost-effectively without relying on generic, blocking APIs.
Q: What was the architectural rationale behind the microservices split in TikiTu? In an event platform, user browsing traffic scales completely differently from ticket purchasing or partner updates. If a major event drops, thousands of users hit the browsing and payment endpoints simultaneously. By decoupling the platform into Next.js/Nest.js microservices hosted on AWS ECS Fargate, we can scale the User and Payment services independently under heavy load without degrading performance for partners managing their events in the background.
Q: How did you approach DevOps and infrastructure automation for TikiTu? I treated infrastructure as a core component of the software development lifecycle, not an afterthought. I wrote modular Terraform scripts to provision the entire AWS ecosystem from scratch—setting up secure VPCs, IAM roles, API Gateways, ECS clusters, and Cognito pools. This ensures that the entire enterprise-grade environment can be brought up, modified, or torn down with a single command, eliminating manual configuration errors completely.
